# 面试与简历素材（电商安全版）

## 一句话定义项目

这个项目不是一个风控算法 demo，而是一个面向抖音电商安全与商家风险运营场景的后端平台骨架。我重点做的是风险事件接入、案件流转、审计留痕、稳定性治理和 AI sidecar 增强，而不是把 AI 放进主判定链路。

## 30 秒讲法

我做了一个电商安全后端平台项目，核心链路是风险事件接入、规则结果沉淀、案件生成、异步投递和运营查询。技术上我用 `Go + Hertz + MySQL + Redis + RabbitMQ` 搭了主链路，又补了幂等、事务 outbox、消费者去重、审计日志、API 鉴权、限流和 Prometheus 风格指标，让它更像一个能上线的后端服务，而不是单点功能 demo。

## 90 秒讲法

这个项目主要对应“后端开发工程师-电商安全”这类 JD。因为这类岗位真正考的，不只是会不会写接口，而是能不能把复杂业务抽象成稳定的服务模块。

我把系统拆成三层。第一层是 Gateway，负责风险事件接入、参数校验、`X-API-Key` 鉴权、限流和案例查询。第二层是存储和异步链路，基于 MySQL 做案件主数据、幂等表、审计日志和 outbox，基于 Redis 做查询缓存和限流，基于 RabbitMQ 做异步投递。第三层是 Worker，负责消费消息、做持久化去重，避免重复投递带来重复副作用。AI Copilot 只做风险摘要和排查建议，不进入主判定链路。

我刻意把 phase 4 做到了比较贴近真实线上服务：入口幂等、异步可靠投递、失败重试、消费者 dedup、按案例查审计轨迹、以及 `/metrics` 暴露运行指标。这样讲项目时，既能体现后端基础，也能体现电商安全场景下的业务抽象和稳定性意识。

## 3 分钟讲法

如果面试官让我完整展开，我会先讲业务问题。电商安全后端不是只做一条规则命中就结束，它还要支撑商家侧产品、运营侧案件处理和专项治理，所以系统必须同时具备事件接入能力、案件流转能力、数据服务能力和稳定性治理能力。

然后我会讲系统设计。主链路是：`risk event ingest -> idempotent persistence -> transactional outbox -> async worker consume -> case query / audit query / metrics`。我没有把消息投递放在“写库之后顺手发一条消息”的 best-effort 逻辑里，而是做成事务 outbox，这样能避免“库里有案件但队列没消息”的不一致问题。为了防止客户端重试和 MQ 重投，我又在入口和消费者两端都做了幂等控制：Gateway 侧按 `X-Idempotency-Key` 或稳定请求指纹去重，Worker 侧按 `event_id` 做持久化去重。

最后我会讲我为什么这么设计。这个项目的重点不是炫技，而是把后端平台岗位真正关心的点讲清楚：接口安全、系统稳定、数据可追踪、模块可复用。比如我加了 `X-API-Key` 鉴权和限流，是为了体现线上服务保护；我加了案件审计查询和 `/metrics`，是为了体现可观测性和运营支持；我把 AI 保持在 sidecar，是为了体现工程边界感，避免模型输出影响主判定链路。

## 面试官高频追问与答法

### 为什么要做两层幂等，而不是只在入口做一次？

入口幂等解决的是客户端重试和重复提交，但 MQ 场景还会有重投和重复消费，所以消费者端还要做一次持久化 dedup。这样才能同时覆盖“请求重复”和“消息重复”。

### 为什么要用 outbox，而不是直接发 MQ？

因为直接发 MQ 会有写库成功但发消息失败的问题。outbox 的价值是把案件、幂等记录、审计日志和待发送事件放在同一个事务里，先保证本地一致性，再异步投递。

### 你这个项目怎么体现电商安全，而不是普通 CRUD？

我不是围绕用户表和订单表做接口，而是围绕风险事件、证据、案件、运营处置和审计链路来设计模型。这个抽象本身就带有电商安全场景特征。

### AI 在这个项目里到底做什么？

AI 只做 sidecar 增强，比如风险摘要、相似案例提示和排查建议。它不直接决定是否建案，也不进入规则主链路，这样能保证系统可控、可审计。
